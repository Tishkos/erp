## Business dates and money (REQ-HARDEN-001 HARDEN-2)

* "Today" is `businessToday()` from `src/server/domain/business-date.ts` (Asia/Baghdad, `ERP_TIMEZONE`); a timestamp becomes a date with `businessDateOf(instant)`. Never `new Date().toISOString().slice(0, 10)` — it is UTC and reads yesterday for the first three hours of every Baghdad day. `tests/integration/hd07-business-today.test.ts` greps for it and fails the build. SQL that needs today binds `${businessToday()}::date`, never `current_date`.
* Money and quantities are compared and summed as scaled bigints (`parseDecimal` / `parseQuantity` / `divideHalfUp` / `toDecimalString`), never as `Number()`; in the browser the same through `src/lib/decimal.ts`. A `Number()` is only ever the last step before `Intl.NumberFormat`.
* A transition reads its row with `FOR UPDATE` (`lock(tx, id)` in payment-applications, loans, customs-pd, payables; `importOf(…, { lock: true })` in landed-cost) before it checks the status, so a double submit posts once. `tests/integration/hd09-double-submit.test.ts` holds it.

## Audit timestamp payloads

Pass timestamps to `audit.record` as ISO strings, not JavaScript `Date` objects: a Date in an audit before-value was serialized as `{}` by the current audit pipeline. Existing audit rows remain immutable; any correction must be an append-only supplement with verified source evidence.

## Inventory: one ledger, and the scripts that must respect it

`inventory_movement` is the only source of stock quantity. `stock_position`, `positionOf`, the Stock Movement page and the Warehouses Report's Quantity column all sum it; `cost_layer` carries the value. Every document that moves stock writes its rows in the same transaction, so the two cannot drift through the application — only through maintenance.

When a new document table that moves stock is added (migration), add it to **both** `tests/integration/setup.ts` (`resetTestData`) **and** `scripts/ops/format-live-database.sh` (`DOCUMENT_TABLES`). The 2026-09-27 orphans (`TRF-HQ-2026-000001/2`, `ADJ-HQ-2026-000001`) were the format script wiping `inventory_movement` while `stock_transfer`/`stock_adjustment` were missing from its list.

To check a live database: `npx tsx scripts/ops/stock-movement-trace.ts [warehouse] [item]` prints every movement with a running balance and runs `services/inventory-integrity.ts` (documents without ledger rows, rows without documents, unbalanced transfers). To remove a verified orphan document: `scripts/ops/remove-orphan-stock-documents.sh [--yes] TRF-… ADJ-…` — it refuses anything that has movements and writes an `audit_event` per removal.

The Warehouses Report's *Total Price* is IQD at FIFO cost, not a quantity and not a selling price: 507 units bought as 10 @ 50 and 500 @ 500 less 3 sold is 250,350 IQD.

Integration suites: `npx vitest run --project integration tests/integration/ops15-inventory-ledger.test.ts` (≈3 min) covers the lifecycle, warehouse isolation, returns, transfers, shipment stages, concurrent double-posting, negative stock, the integrity checks, invoice reversal, the form-id idempotency key, the warehouse-branch rule, the Stock Ledger and paging. `ops16-document-table-lists.test.ts` derives the document tables from the schema and fails if `format-live-database.sh` or `resetTestData` omits one.

## Correcting a posted invoice

A posted AP or AR invoice is **reversed** (`ap.reverse` / `ar.reverse`, the Reverse action on its page), never edited: the journal is mirrored through `journal.reverse`, every stock movement is put back through `inventory.reverseMovement` (onto its own FIFO layers), status → `reversed` with `reversal_reason`. Refused while a payment, return, credit memo or payment run rests on it, or while stock from a purchase has been sold or moved on. The reversal is dated the day it is made, so the current period must be open. A Sales/Goods Return is for goods that come back; a reversal is for an invoice that should not have been posted.

## Stock movements carry the warehouse's branch

`inventory.receive/issue/issueFromLayer` refuse a `branchCode` that is not the warehouse's, and migration 0215 holds the same rule by trigger on `inventory_movement` and `cost_layer`. Pass the warehouse's branch (the actor's, after `usableWarehouse`, is the same thing).

## Transfer and Reconciliation forms carry a one-time id

The page mints a UUID into `document_id`; `stock.transfer` / `stock.adjust` take it as the document's id and answer with the existing document on a repeat. New forms that create a stock-moving document on submit should do the same.

## Logistics (REQ-LOG-001)

* **What it is.** The physical journey of imported goods — Import → Shipment (B/L) → Containers → Customs (PD, declaration) → Landed cost → Goods receipt → Inventory — as four headings and fifteen items (`menu.ts` sections `logistics_customs`, `logistics_shipping`, `logistics_in_transit`, `logistics_landed_costs`; the client jobs' section `logistics` is out of the dropdown, Q3). The old routes keep working (D-FX-1); new screens are `/logistics/…`; only `/inventory/in-transit` redirects (to `/logistics/in-transit`, `next.config.ts`).
* **Reads live in one file.** `services/logistics-views.ts` holds every register the headings show, over the engines' own rows and never recomputing: `dutiesRegister` / `freightRegister` (`landed_cost_charge` by type and state), `documentsRegister` (`attachment` by the record it hangs on — Q6, no category column), `shipmentsRegister` (one row per import with a live B/L), `inTransitInventory`, `transitWarehouses`, `inTransitReconciliation`, `shipmentTracking`, `landedCostsRegister` (the import page's own `lockableState`, said in a word by `domain/import-logistics.lockReason`), `costAllocation` / `locks` (lock → layer adjustment → inventory / COGS → journal), `shippingForImport`, `customsForImport`, `receiptByNo`. Do not add a read to `landed-cost.ts`, `payables.ts` or `inventory.ts` for a Logistics screen.
* **In transit is never on hand.** Stock in a warehouse with `is_transit` or `shipment_stage` is *in transit*: `stock_position` (Inventory's view) counts it in that warehouse's `on_hand` with `available` 0 — `transitWarehouses` reads that row and labels it in transit; `inTransitInventory` reads the posted invoice's cost layers still in transit warehouses (in transit), the container receipts' `moved_qty` (received) and the receipts' own layers (on hand from this import); `inTransitReconciliation` says whether the import rows add up to the ledger per item and reports a difference, never repairs it. 500 shipped, 300 received → in transit 200, received 300, on hand 300 (`tests/integration/log01-chain.test.ts`). `stock_position` itself is Inventory's to change.
* **The customs declaration** (`customs_declaration`, 0301; `services/customs-declarations.ts`, pure rules in `domain/import-logistics.ts`) is what the broker lodged against a PD: declared value, duty, taxes, fees, HS code, in its own currency — **declared figures only**, frozen once it leaves draft (trigger `customs_declaration_frozen`), never posted, never a charge. * **Ports** (`services/ports.ts`, the first writer of `port`): `add` mints from `PORT_CODE` and skips a code a row already holds, `rename`, `deactivate` / `reactivate` with a reason — never deleted; a retired port keeps its old B/Ls and is not offered to new ones. `routesInUse` is what the B/Ls say (loading → discharge), read, never kept. The PD page shows the import's B/Ls and containers (customs and clearance per container) and the declarations against it; the container page and register show the import's PD standing and the clearance date.

## Global search (platform phase, Agent 5)

* **One registry, declarations in `src/server/search/entities/`.** A record type a person looks for is a `SearchTableType` (table `t`, grant, list route, `series`, `number`, `text`, `refs`, `recent`, display columns, `href`) or a `SearchCustomType` (`run(tx, request)`), added to `BUILT_IN` in `entities/index.ts`; `services/global-search.ts` does the rest. The Task Center and Document Center register this way (steps in `docs/audits/GLOBAL-SEARCH-IMPLEMENTATION.md` §8); a type that is only `registerSearchType`'d is unknown to a process that never imported it.
* **Always as the asker, read-only, no memory.** `searchAs` opens the asker's scope in a transaction held `transaction_read_only` with a 5 s timeout; a type is queried only if `can(view, grant.object)` and its list route is served (`visibleRoute`), each type in its own savepoint. Nothing is audited or logged of what was typed. A warehouse (no row policy) carries the branch rule in its `where`; a file is shown only where `attachments.mayAccessParent` allows its parent; an employee never carries an `amount`; an item's price is under `price_list`.
* **LIKE does not run ahead of a row policy.** On a table under RLS only leakproof operators (`=`, `<`, `>=`) may be index conditions; `LIKE`, `lower()`, `search_fold()` and trigram are not, so a trigram index there is never used and the query reads every row the person may see (measured 4–7 s on 300k invoices). So (`search/table-query.ts`): numbers and `refs` are compared as stored over `rawVariants` (equal or `>= x and < prefixUpperBound(x)`) on plain btrees, whole table; `text` is folded LIKE **inside the `CONTAINS_WINDOW` (10,000) newest rows** by `recent`; tables with no policy keep trigram GIN over `search_fold(col)`. Policed tables are read from `pg_class.relrowsecurity` (`rowSecurityTables`). Don't "fix" a slow type by adding a trigram index on a policed table.
* **Index what you declare.** A policed type needs a plain btree on `number` (not only a partial unique), on each `refs` column and `(recent DESC NULLS LAST)` — the order the query asks; `tests/unit/gs-search-indexes.test.ts` reads 0330 and fails otherwise (add a new declaration module to its list). A table with `text` and no `recent` is arbitrary rows past the window.
* **Exact match first.** Tiers: 0 whole, 1 serial, 2 begins, 3 contains, 4 party. A series is read from `doc_sequence` at query time (`TASK-100` works when `TASK` exists); "AP-12" is serial 12 of the series whose prefix begins AP, found through `doc_number_allocation(serial)`. A test that creates a series must expect `resetTestData` to delete `doc_sequence` keys it does not keep. Records need 2 characters, substrings 3; a phrase is cut at 80 characters and 4 words.
* **`search_fold`** (0330) and `domain/search.foldText` are one function in two languages; change both and `gs-global-search` › "agree". Status codes shown on a screen go through `search.status.<code>` and `CHIP`; a type through `search.types.<key>` — both locales, held by `gs-search-domain`.
* **Screens in the results are the shell's list** (`visibleScreens`, held by `gs-global-search` › "screens follow the shell"). `/search` is delivered; the palette is `components/global-search.tsx` (Ctrl/Cmd+K) fed by `GET /search/results`. Palette gaps with existing classes only: no compact group-heading class (reuses `erp-search__empty`), no row-meta classes.
* Tests: `tests/unit/gs-search-domain.test.ts`, `tests/unit/gs-search-indexes.test.ts`, `tests/integration/gs-global-search.test.ts` (own database), `tests/e2e/global-search.spec.ts`.

## Notification centre (platform phase, Agent 6, migration 0350)

* **A notification never changes the act.** An emitting service runs its notice in `notifications.safely(tx, …)` (a savepoint: the notice is undone and logged, the act commits). Workflow submit/decide announce `approval.required` (to the approvers, never the submitter; occurrence = revision:step), `approval.completed` / `approval.rejected` (to the submitter); a bank-account submission keeps its own rule, a journal that the submitter may post themselves announces nothing (`announce: false`).

Read / unread / open are not audited (read state is the person's own convenience). *Mark all as read* is one `notification.marked_all_read` row (object = the user, after `{ count, category }`), however many it changed.

* **A view is a screen's question, never its answer.** `saved_view` (0019) gained `kind` (`list` = the list framework's rows, untouched; `route` = a screen's filters) and `pinned_at`. ## Exception Center (platform phase, Agent 7, migrations 0380–0381)

* **A finding is a fact, stored once.** `exception` (EXC-nnnn, series `EXCEPTION`, kept by `resetTestData`) is keyed by `detector|subject` (unique): the same trouble is one row however many sweeps, however concurrent, find it. It carries the severity, the domain, the affected record (`record_type`/`record_id`/`record_href`), the way to deal with it (`href`), the owner, the `facts` the words are made from and the `evidence` rows (at most 50). `exception_history` (append-only, written by an AFTER trigger) is the road: detected, acknowledged, resolved, reopened, severity raised or lowered. Nothing is ever deleted (`exception_no_delete`); the format script clears them under `session_replication_role = replica` with the other documents.
* **The road is held by the database.** `exception_lifecycle_guard` allows open → acknowledged/resolved, acknowledged → open/resolved, resolved → open, and says who walks which: a **person** takes only open → acknowledged, with a note, and changes nothing else on the row; the **sweep** (`app.system_sweep`, set by `markSystemSweep` in its own transaction) resolves, reopens (a resolved finding found again becomes open on its next occurrence; an acknowledged one reopens only when it got worse) and re-grades. `domain/exceptions.ts` › `allowedPairs` is the same list; the unit test reads the migration and fails if they differ.
* **Detectors only read, and are asked in a read-only transaction.** `services/exception-detectors/*` (one runner per `DETECTORS` entry, held equal by `ex01-exceptions.test.ts`) run as the system operator inside `set local transaction_read_only = on`, each in a savepoint, reusing the services that already know the question (`bank-reconciliation.position`, `subledger.reconciliation`, `open-items`, `inventory-integrity`, `logistics-views`, `tasks.overdueTasks`, `closing-checks`, `system-health` …) — none repeats their arithmetic. A second transaction (advisory lock `exception_sweep`) persists what was found with the pure `plan()`: create, update, touch, reopen, resolve. **A finding not found again is resolved only if its own detector ran without an error**; a detector that failed (or was not asked, `only:`) leaves its findings exactly as they were. The sweep's principal is the scope's: a super user whatever the column says.
* **Facts, not sentences.** A finding stores `facts`; the words come from the message catalogue — `admin.exceptions.detector.<code with . → _>.{name,title,explanation,action}` and `evidence_note.<code>` — in the **viewer's** language (`exception-text.ts`; `title`/`explanation` stored are an English snapshot for search). Fact names carry their formatting by suffix (`…Iqd`, `…Qty`, `…Date`, `…Event`, `…Role`, `…Kind`, `…Detector`, `…Check`, `priority`). A new detector is: an entry in `DETECTORS`, a runner in `RUNNERS`, its catalogue keys in **both** locales (`ex01-exceptions.test.ts` renders every detector with sample facts in both and refuses a raw code, a placeholder or a missing key), a row in the handoff.
* **Who sees what.** `exception_scope` (FORCE RLS): `view` on `exception` **and** on the object the finding is about (`DETECTORS[].object`), in its branch (null branch = the whole company). `exceptions.recordVisible` then asks the one question SQL cannot — may this person open the affected record (`attachments.mayAccessParent`; a task is its parties’ alone; an approval waiting is its approver’s and the workflow managers’). Every read (`openFor`, `countsFor`, `byRecord`, `listForScreen`, `byNo`), the record’s notes, files, print copy and Global Search go through it. `execute` = acknowledge; `administer` (CEO, accounting manager, system administrator) = Refresh now.
* **Reads other screens use** (`services/exceptions.ts`): `openFor(tx, principal, { limit?, domain?, minSeverity? })` → `{ id, no, severity, domain, title, explanation, recordType, recordId, href, createdAt, ownerName }` (open only — an acknowledged finding is somebody’s in hand; `includeAcknowledged` adds them; `href` is the exception’s own page), `countsFor(tx, principal)` → `{ total, bySeverity, byDomain }`, `byRecord(tx, principal, recordType, recordId)` for a record page’s or the Control Center’s “what is wrong here”.
* **Told once.** A NEW critical or high finding, a reopened one and a severity raised to those grades are notified (`exception.<domain>` kinds, window `occurrence`, dedupe `<occurrence>:<severity>`, `recordAccess`) to the holders of both grants in the branch and the owner; low and medium wait on the screen. The kinds sit in the Accounting category (the registry reserves the `exception.` prefix for it). The schedule is `exception-sweep` every 30 minutes (`crontab.erp`, `scripts/ops/exception-sweep.ts`, a live-use script that writes only these tables and notifications); “Refresh now” runs the same sweep, rate-limited to one per 30 s (it answers with the last run).
* **Thresholds are constants** (`THRESHOLDS` in `domain/exceptions.ts`: days overdue → severity, the PD warning, the close grace) — no settings screen yet. A detector shows at most 200 findings and a finding at most 25 evidence rows; more is said by a `platform.sweep_truncated` finding, never dropped silently.
* **What it does not do.** It repairs, posts and edits nothing; nothing here is a business record. Stock cannot go negative through the application (a deferred trigger refuses it), so `inventory.negative_stock` is a net for damage left by maintenance — the integration test makes it with the triggers off. A manual journal on a control account that names no party stays a finding after a correcting journal (both lines still lack a sub-ledger entry) — acknowledge it. `platform.system_health` is host-dependent (the machine’s files and disk) and is the one detector the integration tests leave out.
* Screens: `/exceptions` (the register: domain, severity, status, owner; Refresh now) and `/exceptions/[exceptionNo]` (the four doors in the standing order, evidence, the road, acknowledge). Tests: `tests/unit/ex01-exceptions.test.ts`, `tests/integration/ex01-exceptions.test.ts` (own database; a real world from `logistics-fixture`), `tests/e2e/exceptions.spec.ts`. Controls C-78 to C-81. Record: `docs/audits/EXCEPTION-CENTER-IMPLEMENTATION.md`.

## Workflow Automation (platform phase, Agent 10, migrations 0400–0403)

* The first **controlled** automation layer — not a workflow builder. A rule is one explicit Qimah event (`EVENTS` in `domain/automation-events.ts`: `ap_invoice.submitted`, `ap_invoice.posted`, `task.overdue`, `container.eta_exceeded`, `ar_invoice.overdue`), at most 8 typed conditions and at most 6 actions from a closed set (`create_notification`, `create_task`, `request_approval`, `create_exception`, `open_workflow`), validated by `domain/automation.ts` and again by the database (`automation_rule_version_guard`). **No action posts, pays, moves stock or runs code, and a new action kind is never a posting.** A rule is built from a template (`domain/automation-templates.ts`, five, all born OFF) and the only thing a person types is the template's parameters.
